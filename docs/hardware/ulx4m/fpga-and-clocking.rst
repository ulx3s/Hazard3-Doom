FPGA, Clocking, and I/O Domains
================================

The FPGA is the center of the ULX4M, but the package and speed/feature variant
matter just as much as the family name. Hazard3-Doom's ULX4M-LD target is built
for ``LFE5UM-85F-8BG381C``. The ``UM`` device class includes ECP5 SerDes
resources, while ordinary ``LFE5U`` variants do not provide the same high-speed
transceiver capability.

The current ULX4M-LS Hazard3-Doom makefile targets an 85K ECP5 in the
``CABGA381`` package because the complete Doom SoC requires more block RAM than
a 12K device provides.

25 MHz board reference
----------------------

The project constraints define ``clk_osc`` as a 25 MHz input. That single board
reference feeds several logically independent clock trees.

On ULX4M-LD the important domains are:

.. list-table::
   :header-rows: 1
   :widths: 26 20 54

   * - Domain
     - Nominal clock
     - Purpose
   * - Board reference/init
     - 25 MHz
     - Direct oscillator input and LiteDRAM reference/init clock.
   * - Hazard3/AHB system
     - 40 MHz qualified
     - CPU, SoC bus, resident monitor, UART-side platform logic, and AHB side of the DDR adapter.
   * - LiteDRAM user
     - 60 MHz qualified
     - 128-bit Wishbone user port and controller-side transaction handling.
   * - DDR memory clock
     - 120 MHz in current generated metadata
     - Physical DDR3 transfer clock generated by the LiteDRAM clocking/PHY path.
   * - Video pixel
     - 50 MHz
     - Pixel-domain side of the 1024x600 video pipeline.
   * - TMDS serializer
     - 250 MHz
     - 5x video clock used by the GPDI/HDMI serializer path.

The ULX4M-LD wrapper deliberately keeps LiteDRAM on the direct 25 MHz board
reference while Hazard3 can run from a separate system PLL. This is important:
changing the CPU clock does not automatically change the generated DDR3 timing
profile.

The wrapper currently permits 25, 40, or 50 MHz Hazard3 system selections, but
40 MHz is the qualified release checkpoint paired with the 60 MHz LiteDRAM user
clock. A build option is not the same as a hardware qualification.

ULX4M-LS clocking
-----------------

The current LS wrapper uses the same 25 MHz board reference but generates a
50 MHz Hazard3/SDRAM system clock. Video uses a second PLL so the CPU/SDRAM and
video timing problems can be analyzed independently.

The SDRAM clock forwarded to the physical memory is phase-related to the
50 MHz system clock. The wrapper drives an inverted DDR output copy so commands
and data launched on the system edge arrive with the intended half-cycle timing
relationship at the SDRAM device.

Why clock domains matter
------------------------

An FPGA schematic can make two blocks look adjacent even when they run from
unrelated clocks. Hazard3-Doom's ULX4M-LD memory path is a good example: the CPU
issues an AHB transaction at 40 MHz, while the LiteDRAM user port operates at
60 MHz. ``ahb_litedram.v`` must therefore do more than translate bus signal
names; it must safely move requests and responses between clock domains.

For timing work, always distinguish these questions:

* Does the 40 MHz Hazard3 system domain meet timing?
* Does the 60 MHz LiteDRAM user domain meet timing?
* Are the generated PHY clocks and DDR constraints valid for the selected
  memory profile?
* Does the final routed bitstream pass real memory tests on the actual board?

A nextpnr PASS for one clock is not proof that the complete memory subsystem is
qualified. See :doc:`../../reference/timing-sweeps` for the project's routing
and qualification workflow.

I/O standards are part of the design
------------------------------------

The LPF is not merely a pin-name list. It also tells ECP5 tooling how a physical
pad must behave. For ULX4M-LD, ordinary control/address signals use DDR3 SSTL
I/O settings, DQ and DQS pins use the appropriate bidirectional/differential
forms, and the positive DQS/clock pins are constrained so nextpnr can use the
paired ECP5 differential resources.

For ULX4M-LS, SDR SDRAM and many ordinary board signals use 3.3 V LVCMOS I/O.
The GPDI path in the LS wrapper drives positive and negative pins explicitly as
fake-differential LVCMOS pairs, while the LD implementation uses the board's
selected GPDI mapping for its video path.

This is why copying an LPF from a similar board can be dangerous: a correct
package pin with the wrong electrical standard can still be wrong hardware.
